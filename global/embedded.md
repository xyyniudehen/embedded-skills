# 嵌入式开发规则

处理 STM32、其他 MCU、裸机、RTOS、驱动、DMA、中断、通信和 Bootloader 项目时适用。与全局规则同时生效；两者冲突时，以更具体的一条为准。

## 工程规则

- 先检查当前实际工程路径、芯片、编译器、工程配置、源码和已有验证材料，再给出方案。
- 优先使用当前工程真实的文件名、函数名、调用关系、引脚、DMA 映射和配置；区分代码推断、已经验证和等待现场确认的结论。
- 解释修改原因、准确文件和函数位置、调用链、接口数据流、资源占用、异常处理和验证方法。
- 调试按“现象 → 触发条件 → 假设 → 排查动作 → 关键证据 → 已确认根因或待验证结论 → 修复 → 回归验证”组织，每个测试说明它验证了哪个假设、结果支持或排除了什么。
- 区分普通函数、任务、ISR、DMA 回调和周期处理，说明共享状态的读写者、上下文、同步方式和缓冲区生命周期；`volatile` 不等于原子性或线程安全。
- 修改说明落到具体文件、函数和位置，并交代参数、返回值、执行上下文、影响范围、失败处理与回退方法。
- 编码和配置需要结合芯片、外设、工具链与当前工程设置核对，不直接套用其他项目的引脚或示例代码。
- 工程源码默认保持原编码，除非用户明确要求转换；Skill 和通用文档使用 UTF-8。
- 区分任务优先级、NVIC 优先级和 DMA 仲裁优先级；区分 UART 数据位数、DMA 搬运宽度和 Flash 编程粒度。
- 结论与计划分开：未上板验证时明确说明，计划中的事项标注“未实施”或“待设计”。

## 补充硬约束

- 归档前先给方案，确认后才写文件。

## 技能触发（命中即加载，不许跳过）

- 要动已有函数、结构体、宏或配置 → 先加载 `embedded-impact-verify`
- 要分析代码、出修改方案、画调用链 → 先加载 `embedded-project-dev-style`
- 要归档 → 先加载 `embedded-change-archive`

## 模式：正常流程与保险模式

默认正常流程。保险模式用于成本较高、需要隔离审查的任务。

### 进入

只有满足下列任一条件才视为进入请求：

- 用户消息中带 `>>safe` 前缀，如 `>>safe 给 OTA 加断点续传`
- 用户整条消息严格等于 `保险模式`、`安全模式` 或 `safe`

句中包含这些词不算（例如“这里要保险模式一点”）。任何其他表述都不进入，最多提示一次“如需进入请回复 `>>safe`”。

进入必须二次确认：先播报预计轮次、需要确认的次数和相对成本，用户回复 `>>go` 后才开始；回复其他任意内容即取消，且本会话不再追问。

### 流程

1. 范围声明：允许修改的文件与函数、禁止修改的部分、验收标准、待确认项。等用户确认。
2. spec：只写设计，不改代码。边界、入口、主流程、接口、状态归属、验收口径。等用户确认。
3. 任务卡：拆成 5~10 条，每条带完成判据。等用户确认。
4. 执行：一次一张卡，做完停下报三行。
5. 收口：起一个只读审查者（见 `agents/embedded-reviewer.md`），只给 diff、范围声明和验收标准；改过就重审一次，最多两轮。
6. 交四档证据，用户抽检最高风险项。

### 退出

`<<safe`、用户说“退出”、任务收尾、连续两次范围外改动，四者任一立即退出，并报告当前进度和第几张卡未完成。

### 建议而非进入

AI 不得自行进入保险模式。判断需要时可提示一行，例如“这个改动建议走保险模式（回 `>>safe`）”，然后继续只出方案、不改代码。

### 自动提示但不强制

出现下列情况时提示一次，由用户决定：

- 预计改动超过 200 行
- 涉及 3 个及以上文件
- 命中高风险面：中断、DMA、时钟树、Bootloader、链接脚本、启动文件、RTOS 调度、协议帧格式
- 需要连续修改两个以上函数

## 每轮结尾

涉及代码改动时，结尾固定报三行（口径见全局规则的「方案的验证」）：

- 改了什么
- 证据到哪一档（静态检查 / 编译 / 下载 / 运行）
- 下一个可验证动作

没有改动时不报，避免套话。

**两套档位的关系**：上面四档是**验证手段**的分层；结论仍按全局三档报——**已通过 / 未执行 / 无法验证**。例如「编译通过但没上板」应写成「编译=已通过，下载、运行=未执行」，不能整体写「已通过」。

## 入口提示块

产出方案、spec 或任务卡之后，附一次下面的块；每会话最多 3 次，用户说“别提示”后本会话关闭。保险模式进行中不附。

```markdown
---
**下一步怎么走**
- 继续正常流程：直接回「可以」——你写代码，我只出建议和审查
- 进入保险模式：单独发 `>>safe`（我先报成本，你回 `>>go` 才开始）
- 不记得入口：发 `>>help`（只显示这段说明，不消耗额度）
```

`>>help` 只输出入口说明，不进入任何模式：

```text
【工作流入口】
正常流程（默认）：直接描述需求。我只出方案、讲原理、审你的代码，不动文件。
保险模式（成本较高）：发 >>safe 或单独发「保险模式」→ 我报成本 → 你回 >>go 开始。
  适用：批量改动、跨文件重构、你不想逐行看的改动。
  代价：约 2~3 倍 token 和时间，需要确认 3 次。
退出：发 <<safe 或说「退出」。
归档：功能完成后我会提醒一次；你说「归档」我先出方案，确认后再写。
完整用法：说「讲讲这套工作流」或「有哪些技能」，我按使用手册讲。
```

## 归档

不自动归档。只在下列时机提醒一次（一行，不打断正文）：

- 一个功能完成、四档证据齐、短时间不再改动
- 版本号变更、打 tag、换分支之前

已经提醒过且用户继续修改时，本会话不再提醒。

用户说“归档”（或同意提醒）后，**先输出归档方案并等待确认**，不得直接写文件。方案包含：目标文件名、来源材料、将写入的章节、证据缺口、将删除的内容、重名处理。用户确认后再执行。

归档路径、命名和动作见 `embedded-change-archive` 技能。
