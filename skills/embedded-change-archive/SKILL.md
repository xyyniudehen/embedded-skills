# 嵌入式代码变更归档

将工程代码、变更材料和调试历史整理成准确、简洁、便于长期回顾的文档。突出业务行为变化、设计原因与排错过程，不将归档扩展成逐行代码教程。

## 何时使用

- 一个功能完成、四档证据齐、短时间不会再改动
- 用户说“归档”
- 版本号变更、打 tag、换分支之前
- 只整理已有材料，不回看代码也可以

不适用于：还没实现完、还在调试、只是想让另一个视角找 bug。

## 归档前先给方案（硬性）

用户说“归档”或同意提醒后，**先输出归档方案，等确认后再写任何文件**。方案格式：

```markdown
## 归档方案

- 文件名：更新记录/2026-10-20_OTA断点续传.md
- 主题：Bootloader OTA 断点续传
- 来源材料：_进行中_OTA断点续传/spec.md、git diff、串口日志
- 将写入：摘要 / 改动面 / 与原方案差异 / 调用链 / 状态量 / 配置 / 调试记录 / 四档证据 / 风险 / 复习卡
- 证据缺口：下载和运行未执行，正文标「未执行」
- 将删除：更新记录/_进行中_OTA断点续传/
- 重名处理：无
```

用户确认后执行；用户改文件名、删章节或要求精简时，按用户口径执行。方案未确认前不得创建、覆盖或删除任何文件。

## 路径与命名

- 默认写到项目根下的 `更新记录/`。
- 探测顺序：`更新记录` → `更新纪录` → `docs/更新记录`。已有任意一个就复用它，**不许再新建第二个**。
- 三者都不存在时才新建 `更新记录/`。
- 文件名：`YYYY-MM-DD_主题.md`，日期取功能完成那天，不用开始日期，也不用归档动作发生的日期。
- 同一天同主题重名时追加 `_2`、`_3`，**绝不覆盖已有文件**。
- 主题用简短中文或 kebab-case，能一眼看出功能，如 `OTA断点续传`、`usb-enum-fail`。
- 活跃期的过程文件放 `更新记录/_进行中_主题/`（`spec.md`、`task_plan.md`），归档完成后整个目录删除。
- 找不到项目根时停下来问，不默认写到当前工作目录或仓库根。

## 归档动作

1. 确定文件名，检查重名。
2. 按 [归档模板](references/archive-template.md) 写正文，按规模裁剪章节。
3. 若存在 `更新记录/_进行中_主题/spec.md`，把其中的设计要点并入「原方案」一节，不原样复制全文。
4. 删除 `_进行中_主题/`，包括 `task_plan.md`、临时截图和整段原始日志。关键日志片段已内联进调试记录。
5. 自检：目录下无 `_进行中_` 残留、文件名符合日期格式、没有覆盖旧文件、归档中的结论与证据表一致。
6. 报告：写入路径、包含章节、证据缺口、删除清单。

## 范围与材料

- 默认只生成归档，不修改源码、不提交 Git、不上传仓库；额外操作按用户授权执行。
- 输入可包含历史对话、代码、Git diff 或提交、编译日志、串口输出、波形和测试记录。
- 使用本次提供的工程路径。先核对版本与范围，需要结构参考时读取[归档模板](references/archive-template.md)。
- 名称、原型、单位、配置和路径严格来自材料；区分已有开源代码、本次改动以及仅提出但未应用的方案。
- 当前代码说明现状，历史材料说明过程。两者冲突时说明差异，不用当前代码反推历史事实。
- 不编造函数、调用关系、日期顺序、测试数据或修复结果。顺序不完整时按已知阶段整理并说明。
- 读取源码注意编码；未经授权不转换编码。

## 证据边界

重要根因和验证结论按需标注“已确认”“根据代码推断”“待验证”，不必给每句话打标签。

- 已确认：材料或实测直接支持。
- 根据代码推断：代码能够支持，但未完成运行验证。
- 待验证：证据不足或仍存在其他解释。
- 未执行：明确知道该做但没做，归档中必须写出来，不能省略。

必要时纠正历史中被证伪的判断。不能把助手建议的实验写成用户已执行，也不能在缺少 CPU 现场时声称追踪到具体异常指令。

## 文档组织

开头用 3 至 5 句话总结目标、核心改动、关键问题及验证结果。主体区分“代码现状”“功能开发与验证”“真实故障排查”，按规模裁剪模板：小改动合并章节，无关章节省略。

代码现状包括目标与文件清单、修改前后行为、关键状态、调用关系、数据流及相关配置。调试过程包括触发条件、关键假设与证据、根因、修复、实际验证和遗留事项。

### 与原方案的差异（新增必写项）

只要本次改动存在设计稿、spec、任务卡或事先讨论的方案，就写一张差异表：

| 原计划 | 实际实现 | 原因 | 影响范围 |
| --- | --- | --- | --- |
| 进度存 RTC 备份寄存器 | 改为 Flash 备份区 | 备份寄存器只有 20 字节，存不下分片位图 | ota.c、flash_map.h |

- 只写最终状态，不写“试过 A 不行换 B”的完整过程；过程放在调试记录里。
- 没有设计稿时，本节写“无事先方案，按现场需求实现”，不硬编内容。
- 差异必须能给出来源，不能凭印象补。

## 状态量

只记录与本次变更相关的全局、静态持久状态、共享对象和关键结构体成员；不列普通临时局部变量。

说明类型、相对文件路径、作用域、状态含义、读写者与执行上下文、volatile 或同步措施。结构体注明成员增删和语义变化。volatile 不等于原子性或线程安全。

## 调用链和函数释义

- 默认用一个 Markdown text 代码块呈现完整主调用树（├──、└── 和缩进），从顶层入口连续展开到本次关键处理与结果，不将同一主线拆成总览和多个需要读者拼接的子树。每个关键函数附一句短职责，不用函数表格代替调用链。
- 一级阶段之间用保留父级竖线的空行留白，二级及以下调用紧凑排列；按业务阶段分组，而非给每个节点加空行。函数细节放树下，避免节点长句和无关库函数使树过密；不以固定深度截断理解所需的链路。
- 明确区分普通调用、硬件触发、中断/回调通知及周期执行。中断不能误画成启动函数直接调用。
- 主树保留业务整体关系，异步 ISR 作为旁侧短树或一条交接说明；不同独立任务才按需要分别画树。硬件触发不嵌入普通调用树。标准库/HAL 仅列必要叶子节点，缩进必须符合真实直接调用关系。
- 树下用短段落或条目详细解释本次新增或显著修改的业务函数：实际原型、所在文件、作用与修改原因、上下文、参数和单位、缓冲区生命周期、返回值、状态变化、阻塞和错误处理、相关同步措施。
- 其他函数只保留一句释义。数据流与调用链重合时合成一张图。
- 按实际架构描述交接：裸机可以是“DMA → ISR 置标志 → 主循环”，不强行写成任务通知。

## 配置与兼容性

只记录本次相关配置：时钟和引脚、DMA 映射/方向/宽度/数量/地址递增、缓冲区边界、NVIC 与挂起标志、RTOS 节拍/栈/堆/优先级、Flash 分区/编程粒度、链接地址/VTOR，以及工程源文件和编译配置。

区分任务优先级、NVIC 优先级、DMA 仲裁优先级；区分 UART 数据位数、DMA 搬运宽度和 Flash 编程粒度。风险判断基于本次材料，不输出无关的通用风险清单。

## 调试与测试

正常新增功能、测试通过和版本演进放开发记录，不标成 Bug。静态发现的潜在缺陷与实测故障分开标注。每个真实问题按真实证据支持的顺序记录：现象和触发 → 当时假设 → 工具、观察和范围缩小 → 根因依据 → 修复位置与原理 → 验证结果 → 一条具体经验。

合并重复尝试，保留关键判断转折。测试分成已执行结果、针对本次改动的建议补测、材料不足的待确认事项。

### 四档证据

验证结论按四档报告，与 `embedded-impact-verify` 保持一致：

| 档位 | 含义 |
| --- | --- |
| 静态检查 | 只读代码和配置，未构建 |
| 编译 | 构建通过 |
| 下载 | 已烧写进目标板 |
| 运行 | 板上实际跑通并观察到现象 |

未执行的档位写“未执行”，并说明原因。区分编译通过、功能测试和压力测试；无证据不写长期稳定、测试小时数或提升百分比。

## 后续计划

- 当材料中存在用户讨论过或明确提出的后续方向时，可在测试与待确认事项之后增加“后续计划”。
- 每项简要说明目标、当前原因或限制、下一步方向；信息不足时标为待设计，不自行补造实现细节。
- 明确标注“计划/未实施”或“待设计”，不能混入本次已完成改动、已验证结果或测试结论，也不能写成必然承诺。
- 仅记录与本次变更直接相关的方向。没有明确计划时省略本节，不自行发明路线图。

## 复习卡（默认生成）

归档末尾固定生成一节，用于日后复习和面试讲述。小改动可只写三条，不强行凑满。

```markdown
## 复习卡

- 核心问题：一句话说清这次解决了什么。
- 最容易被追问：为什么选 A 不选 B？（附一句话理由和证据）
- 如果重做：会改哪一处，为什么。
- 可延伸：与本次改动相关的 2~3 个问题（时序、掉电一致性、资源占用、中断安全等）。
```

规则：

- 只写能讲清楚的，不堆术语。
- 追问项必须有本次归档中的证据支撑，不写“因为惯例”。
- 不把没验证的推断写成结论。

## 精简和交付

- 同一信息只详细解释一次，其他位置引用；不重复背景、根因与修复。
- 已完成工作、真实故障、测试结论与后续计划分开陈述。
- 不罗列所有 API、小错误、无关变量；配置用紧凑表格。
- 后续优化只在用户要求或有明确遗留问题时加入。
- 精简不能省略根因证据、接口行为变化、执行上下文、验证边界和重要待确认事项。
- 正文优先仓库相对路径；需要源码跳转时提供当前实际绝对路径与行号链接。
- Skill 内部用相对引用，不写死电脑、用户、盘符或工程。归档默认写到项目根 `更新记录/`，路径规则见上文。
- 调用链默认树形文本，数据执行顺序默认简短文字箭头。仅在用户要求或图能明显帮助理解时用 Mermaid，且附自然语言说明。Word 中的树用等宽字体，不强制渲染复杂图。避免把调用、数据流和控制流混在一张大图里。
- 交付前核对名称、配置、图中关系、关键函数释义、结论与证据一致性，以及文档可读性。只报告实际执行的文件、中文、渲染和版式检查。
