# 可裁剪的归档模板

按变更规模合并或省略章节，不为完整模板制造内容。

## 变更摘要

3 至 5 句话交代目标、改动、关键问题和实际验证结果，并标注结论的证据档位（已确认 / 代码推断 / 待验证 / 未执行）。

## 第一部分：代码现状

1. 变更概述与影响面：目标、模块、文件清单；有材料时注明版本。
2. 前后对照：原行为、新行为、原因及接口变化。
3. 与原方案的差异（有 spec、设计稿或事先讨论时必写）：

   | 原计划 | 实际实现 | 原因 | 影响范围 |
   | --- | --- | --- | --- |
   |  |  |  |  |

   没有事先方案时写“无事先方案，按现场需求实现”。
4. 状态量：持久/共享状态及读写上下文，同步措施。
5. 调用链与函数：默认一棵完整主调用树，一级阶段间用竖线空行留白、子调用紧凑，每个函数附短职责；异步中断旁侧补充，不能打断主线。重点函数在树下解释原型、参数、返回值、上下文和错误处理。
6. 数据流与配置：与调用链重合时合并，记录本次相关的硬件、缓冲区、通知、时钟和内存配置。

## 第二部分：功能开发与验证

正常功能新增、版本演进与测试记录，不能包装成故障。

验证证据按四档报告，未执行的写“未执行”并说明原因：

| 档位 | 是否执行 | 命令或操作 | 结果 | 覆盖本次改动 |
| --- | --- | --- | --- | --- |
| 静态检查 |  |  |  |  |
| 编译 |  |  |  |  |
| 下载 |  |  |  |  |
| 运行 |  |  |  |  |

## 第三部分：真实故障排查

7. 真实排查时间线：现象、假设、证据、根因、修复、验证；标明重要结论可信度。
8. 测试与遗留事项：已执行、建议补测、待确认分开记录；待确认项标注“影响正确性：是/否”。

## 后续计划（仅在材料提供时保留）

| 目标 | 当前原因或限制 | 后续方向 | 状态 |
| --- | --- | --- | --- |
| 仅填写本次变更直接相关的方向 | 说明现状或动机 | 写已讨论的下一步；未定细节注明待设计 | 计划，未实施 |

## 复习卡（默认保留）

- 核心问题：一句话。
- 最容易被追问：为什么这样选？附证据。
- 如果重做：会改哪一处。
- 可延伸：2~3 个相关问题。

## 裁剪规则

- 小改动只保留：摘要、前后对照、调用与函数说明、四档证据、复习卡。
- 无故障时省略第三部分，不把功能开发写成 Bug。
- 无后续计划时省略该节，不发明路线图。
- 局部改动不写完整调用树，只画受影响的分支，并说明父级入口。
- 只有在材料可确认时写 Git 提交信息。
